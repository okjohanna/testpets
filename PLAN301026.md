# Plan: Cap Task Creation

Add a fixed maximum of 20 tasks at the pure game-rule boundary. `addTask` will reject only new additions when the current task count is already 20, return the existing state, and emit the existing bad-event/toast mechanism. Existing saves with more than 20 tasks will be preserved and remain manageable by delete, reorder, and toggle. Loading will not trim or destroy work. No persisted `taskLimit` field or state-version migration is needed.

## Steps

1. Add an exported `MAX_TASKS = 20` constant beside the existing task rule constants in `src/game.ts`.
2. In `addTask`, keep blank-title validation first, then reject at the cap before generating an id or mutating state. Return the same state reference and a clear bad message such as `You can have up to 20 tasks.` so the controller's existing `run` path renders the toast and saves consistently.
3. Keep `normalizeState` non-trimming: it should continue accepting valid saved tasks above the cap so an update cannot silently delete user data. Document this enforcement boundary near the constant or rule if needed, without adding unrelated refactoring.
4. Preserve the submitted title when the add is rejected. The current `src/ui.ts` submit handler clears the input unconditionally, so adjust the narrow `onAddTask` contract/controller path to report whether the action was accepted, and clear/focus behavior only after a successful add. Blank-title behavior may continue to clear or remain consistent with the existing flow; the cap case must not silently discard typed work.
5. Extend `src/game.test.ts` task tests:
   - Adding the 20th task succeeds.
   - Adding the 21st task is rejected with unchanged state and a bad event.
   - A state containing more than 20 valid tasks is preserved by `normalizeState`.
   - A rejected add does not append a task or consume an id indirectly.

## Relevant Files

- `src/game.ts` - owning rule boundary: `MAX_TASKS`, `addTask`, and intentionally unchanged `normalizeState`.
- `src/game.test.ts` - focused boundary and save-preservation tests.
- `src/main.ts` - adapt the add-task handler only if needed to return acceptance while retaining the existing `run`/toast/save flow.
- `src/ui.ts` - preserve rejected input by using the handler result; no task-state logic belongs here.
- `index.html` - no required change; the existing form and toast/status surface are sufficient.

## Verification

1. Run `npx vitest run` and confirm the new cap and normalization tests pass with the existing suite.
2. Run `npx tsc --noEmit` to validate the handler contract changes.
3. Run `npm run build` for the production bundle.
4. Manually verify: add 20 tasks, attempt a 21st, see a clear limit message, confirm the typed 21st title remains in the input, delete one task, and confirm the retained title can then be added. Restart with an over-limit save only if such a save is available; verify tasks are not trimmed.

## Decisions

- Chosen policy: fixed hard cap, not a user-configurable setting or soft warning.
- Chosen maximum: 20 tasks.
- Existing over-limit saves: preserve tasks; enforce only on new creation.
- Scope excludes the broader future code rewrite, persisted settings UI, task archiving, pagination, and visual redesign.

## Options Considered

- Fixed hard cap: smallest change, deterministic, easy to test, and matches the current pure `game.ts` architecture. Recommended and selected.
- User-configurable cap: flexible, but requires new persisted state, settings UI, validation, migration, and decisions about lowering the cap.
- Soft cap/warning: less disruptive, but does not satisfy the requirement for a maximum.
- For old saves, trimming is strict but destructive; preserving is safer and lets deletion bring the list back under the cap.
